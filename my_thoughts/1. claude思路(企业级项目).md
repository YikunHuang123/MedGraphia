> 开发一个“基于 GraphRAG 的医疗领域知识图谱与大模型协同问答系统”的企业级项目。要求用上现在工业上最流行的技术，要求支持多语言，至少支持中文英文德语，各种技术选型都是经过深入思考和对比的。我们先来完成这个架构吧，我们需要实现什么功能，数据怎么获取，用爬虫吗？步骤要怎么样，每一步的技术算法选择是什么。请你上网搜索，一步一步思考。注意：这是实际企业生产项目，要求一切功能流程，都满足目前工业上的应用标准。

我已经把当前工业界的主流技术栈和医疗 GraphRAG 的工程实践都研究了一遍，下面给出一份完整的企业级架构方案。这不是教科书式答案，而是按"在法兰克福做欧洲/中国/英语市场医疗产品"的真实场景做的工程选型。

在写架构之前，我必须先打掉一个常见误区，否则后面所有设计都站不住脚——

### 一、关于"爬虫"的硬性结论

**企业级医疗系统绝对不能用爬虫做数据源** ，原因不是技术问题而是合规和质量问题：

1. **法律风险** ：你在德国，受 GDPR 第 5、9 条约束（健康数据属"特殊类别"），还要满足《欧盟 AI 法案》对高风险系统的要求；如果产品入华还有 PIPL 和《生成式 AI 服务管理暂行办法》；做美国市场就要 HIPAA + BAA。爬医疗网站不仅违反 ToS，几乎一定违反这几部法律。
2. **数据质量** ：医疗领域错一个剂量、一个剂型映射就可能要命，开放网页的事实可信度无法做溯源审计。
3. **可追溯性** ：监管要求每一条答案能 trace 到权威信源（FDA Label、欧洲药品管理局 SmPC、AWMF S3 指南、国家药监局说明书等）。爬来的网页给不了 OID/version。

**正确做法** ：用受版权许可、有版本号、有 OID 的 **权威结构化资源** ，配合企业内部受控文档（医院 EHR/SOP）。下面会列清单。

### 二、系统要实现的功能（Scope）

按企业级医疗产品的实际诉求，分四类用例：

1. **临床决策辅助问答** ：医生输入患者主诉/化验单 → 系统结合症状、疾病、药物、相互作用、指南条款给出可解释的鉴别诊断和方案建议（带证据链）。
2. **药学/合规问答** ：剂量、相互作用、禁忌、孕妇/儿科调整、医保目录匹配。
3. **医学文献综述/科研问答** ：跨 PubMed/Embase 的多跳综合问答（这是 GraphRAG 的核心优势场景）。
4. **患者侧科普问答** ：分级降语，多语种输出，强制免责声明和"请就医"路由。

四个场景共享同一套底层 KG + 向量库，但 prompt、guardrail、可输出范围不同。

### 一、数据源层（不爬虫，用授权信源）

按"权威性 → 多语言覆盖 → 内部数据"三类来组织。

**本体与术语（多语言主骨架）** ：以 **UMLS Metathesaurus** 作为跨语种的中枢，因为它本身就跨 25 种语言映射了 200+ 术语集（SNOMED CT、ICD-10/11、MeSH、LOINC、RxNorm 等）。但要注意 UMLS 自身并不直接支持中文查询，所以中文侧另外引入 **CMeKG** （中文医学知识图谱）和 **ICD-10/11 中文版** 做补齐。德语侧用 **ICD-10-GM** 、 **ATC-DDD** 、 **Alpha-ID** 以及 BfArM 的本体扩展。这三套通过 UMLS CUI 做交叉对齐——这是后面跨语种检索的关键。 [Medium](https://dgg32.medium.com/building-a-multilingual-medical-dictionary-as-a-graph-database-e9cdc579123d)

**文献与指南** ：英文用 PubMed 的 **E-utilities API** （NCBI 官方、合规）、Cochrane Reviews（需许可）、ClinicalTrials.gov；德语用 **AWMF S 3-Leitlinien** （医学学会联盟的诊疗指南，开放下载）；中文用国家卫健委发布的临床路径与诊疗规范、CNKI（需机构订阅）。 **绝不用爬虫** ，全部走 API 或官方 bulk download。

**药品与说明书** ：DrugBank（学术免费 / 商用需许可）、 **EMA SmPC** （欧洲药品说明书 XML 下载）、 **FDA DailyMed** 、中文用国家药监局公开药品说明书数据集、ATC 编码。

**内部数据** ：FHIR R5 接口拉医院 EHR、内部 SOP/培训资料、临床试验内部数据。这部分是企业差异化的真正核心。

> **关键合规动作** ：你在法兰克福，所以默认按 **GDPR + 欧盟 AI 法案** 走（医疗 QA 在 AI Act 下基本会落到"高风险 AI 系统"），内部数据进入管道之前 **强制经过 PII/PHI 去标识层** （推荐 Microsoft Presidio + 自训练的医疗 PHI 模型，因为 Presidio 对德文医疗实体覆盖不全）。中国市场上线要走 PIPL 的健康数据本地化；美国市场要 BAA。

### 二、构建管道（离线 + 增量）

调度用 **Airflow 2 或 Prefect 3** （Prefect 在 ML pipeline 上更现代，对 Python-first 团队更友好；Airflow 在传统数据团队更稳）。容器化 Kubernetes。

#### 2.1 文档解析与 OCR

**选型：Docling（IBM 开源）做主力，MinerU 处理中文 PDF，Tesseract 5 + PaddleOCR 兜底扫描件**

- **被淘汰** ：Unstructured.io 在英文场景不错但对中文版式（双栏期刊、繁体）较弱；PyMuPDF 不能理解版式语义。
- **为什么是 Docling** ：IBM 2024 年开源，对医学论文的表格、公式、参考文献结构化能力是目前 OSS 里最好的；输出 DoclingDocument JSON，可直接喂给后续 chunker。
- **MinerU** 专门优化中文学术 PDF，对中文医学文献（症状表格、方剂配伍表）的还原率明显更高。

#### 2.2 切块与多语言归一化

**选型：基于语义结构的分层切块（section → paragraph → sentence），非定长切块**

- 不要用 fixed-size 512 tokens 切块——医学文档"剂量段落"被切散就是事故。
- 用 ==Docling 输出的章节树==做 ==anchor-aware chunking==，每个 chunk 带 `section_path` 元数据（"Methods > Dosing > Pediatric"）。
- **语言检测** ：fastText-langid（轻量）+ CLD3（兜底），混排文档按段落级别打标。
- **归一化** ：单位、剂量、温度、时间。强烈建议建一个领域 normalizer（如把"每日两次"、"bid"、"2 x täglich"、"q 12 h"统一到 FHIR Timing）。

#### 2.3 多语言医学 NER

这是==医疗 GraphRAG== 与==通用 GraphRAG== 的==最大差异点==。通用 <font color="#ff0000">GraphRAG</font>（如 Microsoft GraphRAG）默认<font color="#ff0000">让 LLM 直接抽实体</font>，对医学领域 **<font color="#ff0000">误抽率</font>太高、成本太高** 。正确做法是 **==专业模型抽实体 + LLM 抽关系==** 的混合流水线。

**选型：GLiNER-biomed（多语言零样本）+ 各语言领域模型回退**

- **英文** ：BioBERT / PubMedBERT / Clinical-Longformer
- **中文** ：基于 Lattice-LSTM / ClinicalBERT-CN 的领域 NER（参考 融合 ClinicalBERT 与 TransE 知识图谱嵌入、BIOES 标注、BiLSTM + CRF 的中文 EMR NER 方法） [nih](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12457354/)
- **德语** ：GerMedBERT、bert-base-german-clinical
- **被淘汰** ：纯 spaCy / SciSpacy 多语言覆盖不够；纯 LLM NER 在生产是赔钱货（QPS、稳定性、成本三杀）。
- **GLiNER-biomed** 的价值是零样本 + 多语言 + 可指定标签集，先粗筛再用领域模型精排。

#### 2.4 实体链接（跨语言对齐到 UMLS CUI）

**选型：SapBERT-XLMR（跨语种）+ BM 25 候选生成 + 重排**

这一步是多语言体系的"灵魂"：中、英、德的"心肌梗死 / myocardial infarction / Myokardinfarkt"必须落到 **同一个 CUI（C 0027051）** 。否则知识图谱会出现语言相同实体的重复节点。

- SapBERT 通过对 UMLS 同义对做对比学习，跨语种把同概念表面词拉到同向量空间。
- 流水线：mention → BM 25 召回 top-50 candidates → SapBERT cross-encoder 重排 → 阈值过滤 + 人工抽检。
- **被淘汰** ：MedCAT 偏英文；BioSyn 单语；纯 LLM 链接成本极高且不稳。

#### 2.5 关系抽取与图构建

**选型：Schema-guided LLM 抽取，参考 Microsoft GraphRAG，但裁剪到医学 schema**

- 定义封闭的医学 schema（FMA 解剖、SNOMED 关系层），减少 LLM 自由发挥。
- 关系类型限定如：`treats`, `causes`, `contraindicates`, `interacts_with`, `dosage_for`, `symptom_of`, `complication_of`, `coded_as`。
- 用 LLM 在 chunk 内部做关系抽取，每条边带 `evidence_text`、`source_id`、`chunk_id`、`confidence`、`extracted_by_model_version` —— **这就是可追溯性** 。
- 用 **Leiden 算法** 做社区发现（GraphRAG 和 nano-graphrag 都用），为 global query 生成多层 community summary。GraphRAG 和 nano-graphrag 都支持 Leiden 算法。 [Substack](https://aiexpjourney.substack.com/p/microsoft-graphrag-vs-nano-graphrag)
- **成本控制** ：Microsoft GraphRAG 索引一万份文档要 $50-200，而 LightRAG 能在 1/100 的成本下达到 70-90% 的质量。所以 **生产建议** ：用 **LightRAG 作为框架底座** ，把 Microsoft GraphRAG 的 community summary 思路移植过来——这是 2026 年最实际的工程选择。 [Paperclipped](https://www.paperclipped.de/en/blog/graph-rag-production/)

#### 2.6 向量化

**选型：BGE-M 3 主嵌入 + SapBERT 实体嵌入**

- BGE-M 3 一个模型同时输出 **dense（语义）+ sparse（词法）+ ColBERT（多向量）** 三种表示，支持 100+ 语言、最长 8192 token、在英文和其他语言上超过 OpenAI 等模型。 [Hugging Face](https://huggingface.co/BAAI/bge-m3)
- **被淘汰对比** ：
    - OpenAI text-embedding-3-large：闭源、医疗+德语效果不及 BGE-M 3、API 不能本地化（GDPR 风险）
    - multilingual-e 5-large：只有 dense，没 sparse
    - Voyage-3：闭源，不能自托管
- 实体节点用 SapBERT 嵌入存一份，文本 chunk 用 BGE-M 3。两路向量对应 **两种不同的检索路径** 。

### 三、存储层

**==Neo 4j 5.x 作为知识图谱主库==** ：原因不是技术最炫，而是它的生态最成熟——<font color="#ff0000">Neo 4j 的 GraphRAG 集成</font>与 <font color="#ff0000">LangChain</font>、<font color="#ff0000">LlamaIndex</font> 开箱即用，企业级 ACL、备份、Cypher 优化器都久经考验。被淘汰的：NebulaGraph（超大规模更强但企业生态弱）、TigerGraph（闭源、贵）、ArangoDB（多模型但 graph 性能不够）。 [BuildMVPFast](https://www.buildmvpfast.com/blog/graphrag-vs-vector-rag-knowledge-graph-ai-2026)

**==Milvus 2.5== 作为==混合向量库==** ：原生支持 dense+sparse 混合检索，可以直接用 BGE-M3 的三种输出。==被淘汰的==：<font color="#ff0000">Pinecone</font>（闭源 + GDPR 顾虑）、Weaviate（不错但社区不如 Milvus 大）、==Qdrant==（很优秀，如果团队规模小用 Qdrant 也合理）。

**MinIO + Apache Iceberg** ：原始文档、解析中间产物、provenance 日志。Iceberg 给数据科学侧做版本快照。

> 重要：知识图谱节点上 **反向存原文档 chunk_id 与位置** ，回答时能精确定位"这条结论来自 SmPC 第 4.2 节第 3 段"，这是医疗合规审计必须有的能力。

### 四、查询管道（在线）

这一层决定用户体验。

#### 4.1 查询理解与路由（Agent）

**选型：LangGraph 编排，DSPy 写 prompt 模块**

- LangGraph（LangChain 的图状 agent 框架）适合做有状态、有回退、有条件分支的医疗 QA。
- 路由器先判断：①事实型单跳问答 ②多跳推理 ③跨文档综合 ④药品交互查询 ⑤患者侧科普——五种走不同检索策略。
- **语言路由** ：检测查询语言，但允许跨语种检索（中文问题可以命中德文/英文证据，因为我们已经按 CUI 对齐）。

#### 4.2 混合检索（GraphRAG 的核心）

这是和普通向量 RAG 的本质差异。三路并行：

1. **图检索（Graph traversal）** ：先用 NER+EL 把查询里的实体落到 CUI，然后在 Neo 4j 上做 1-2 跳遍历，召回相关子图。
2. **向量检索（Dense + Sparse hybrid）** ：用 BGE-M 3 三种输出做 hybrid search on Milvus，按 RRF（Reciprocal Rank Fusion）合并。
3. **全局检索（Community summary）** ：对"What are common comorbidities of T 2 DM across all our guidelines"这种综合性问题，从 Leiden community summary 检索。Microsoft GraphRAG 的 community summary 在跨整个语料的综合性查询上比向量检索的全面性高 26%、多样性高 57%。 [Paperclipped](https://www.paperclipped.de/en/blog/graph-rag-production/)

三路结果送到下一步。

#### 4.3 重排

**选型：bge-reranker-v2-m3** （与 BGE-M 3 同家族，多语言 cross-encoder）。被淘汰：Cohere Rerank（闭源）、ColBERT（指标好但工程复杂）。

#### 4.4 LLM 生成（多层模型策略）

不要一个模型走天下。按场景分层：

- **高风险临床决策辅助** ：闭源旗舰（GPT-4.x / Claude / Gemini），通过 **Azure OpenAI 或 Vertex AI 的 BAA 通道** （美国侧）或者 **通过 Anthropic/OpenAI 的 EU 数据驻留** （欧洲）。
- **通用问答** ：自托管开源——Qwen 2.5 / DeepSeek（中文最强）、Llama 4 70B（英文）、 **LeoLM 或 EuroLLM** （德语原生）、 **MedGemma / Me-LLaMA / BioMistral** （医学专精）。BioMistral 基于 Mistral 在 PubMed 上预训练，支持 8 种语言的多语言医学能力。 [Picovoice](https://picovoice.ai/blog/medical-language-models-guide/)
- **路由策略** ：用 ==LLM Router==（如 RouteLLM）按<font color="#ff0000">问题复杂度</font>+<font color="#ff0000">风险等级</font>动态选模型。

**推理服务** ：vLLM 或 ==SGLang== 自托管， **TensorRT-LLM** 用于 GPU 最高吞吐场景。

#### 4.5 安全护栏（Guardrails）

医疗场景下这一步 **比生成本身重要** 。

- **输入** ：Llama Guard 4 / NVIDIA NeMo Guardrails 拦截 jailbreak、自残相关、用药寻求。
- **输出** ：检查是否给出诊断/处方（除非定向给医生角色）；强制添加免责声明；幻觉检测（用 RAGAS 的 faithfulness 在线评分，低于阈值则降级回答或转人工）。
- **强制引用** ：每个回答必须能 trace 到具体 chunk + 信源版本号。无可引用证据时 **拒绝回答** 而不是编。

### 五、应用层

> 这部分先用 FastAPI 做后端，streamlit 做后端。后续再重构。

**FastAPI + gRPC** 后端， **Next.js + Vercel AI SDK** 前端（支持 SSE streaming）。

**多租户与权限** ： **Keycloak** 做 SSO， **Open Policy Agent (OPA)** 做行级 ACL——医生、药剂师、研究员、患者四种角色看到的可引用文档范围不同。

**国际化** ：UI i 18 n 用 next-intl，但更重要的是 **模型侧 i 18 n** ——同一个 CUI 在不同语言下输出对应语言术语和本地化的剂量单位/给药习惯。

### 六、横向能力：合规、观测、评测

这部分常被外包公司省略，但企业生产 **必须有** 。

**合规** ：所有 LLM 调用走自托管 LiteLLM gateway，统一审计日志；PHI/PII 全链路加密（KMS-backed）；数据本地化按市场分集群（EU/CN/US）；模型卡（Model Card）与 DPIA 文档化。

**观测** ： **Langfuse 自托管** （开源 + 可自托管，符合 GDPR，跟踪每次 LLM 调用的 prompt、token、延迟、成本、用户反馈）。被淘汰：LangSmith（闭源云端，欧洲合规有顾虑）；Datadog 太重。

**评测** ：

- **离线** ：自建医学 golden set（中英德各 500+ Q&A，由临床顾问标注）+ 公开基准（MedQA、MedMCQA、PubMedQA、CMB 中文医学基准、GerMedQA）+ RAGAS 四项指标（faithfulness、answer relevance、context precision/recall）。
- **在线** ：A/B 测试 + 用户反馈回流 + 红队定期对抗测试。
- **回归** ：CI 每个版本跑 golden set，分数下降阻断发布。

### 七、关键选型小结（被对比掉的方案）

### 下一步建议

如果同意这个总体架构，我建议下一步按这个顺序细化：
